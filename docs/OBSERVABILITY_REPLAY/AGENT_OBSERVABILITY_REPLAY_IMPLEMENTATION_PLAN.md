# Agent 链路观测、回放与故障诊断实施计划书

## 1. 文档目标

在 `docs/AGENT_OBSERVABILITY_REPLAY_PLAN.md` 已完成方案设计、且上下文工程已具备落地基础的前提下，输出一份面向实施阶段的计划书，用于指导 Agent 链路观测、回放与故障诊断能力的分阶段建设、联调、验收与风险控制。

本计划书不展开具体代码实现，重点回答以下问题：

- 先做什么，后做什么
- 每个阶段交付什么
- 与上下文工程如何衔接
- 规则引擎诊断如何先落地，同时如何为 LLM 辅助诊断预留扩展口
- 如何定义验收、风险与上线边界

## 2. 建设目标

本期建设目标是将现有“事件流 + 时间线”的零散能力，升级为可用于实时观测、事后复盘、执行回放和故障诊断的统一运行观测系统，并满足以下要求：

- 统一以 `run -> span -> event -> checkpoint -> diagnostic_issue` 组织 Agent 执行链路
- 与上下文工程打通，能够关联 `contextPackId`、注入摘要、被裁剪上下文和相关 memory 来源
- 支持实时观测与事后复盘两类使用场景，但采用分阶段交付策略
- 诊断能力第一阶段采用规则引擎，优先覆盖高频问题，并预留 LLM 辅助诊断接口
- 观测数据默认结构化、可追溯、可控成本、可脱敏、可按保留期清理

## 3. 范围定义

### 3.1 本期范围

- Agent 运行数据模型统一
- 事件归一化与链路串联
- 实时观测 UI 与诊断面板
- 事件日志持久化基础能力
- 断线重连后的事件补偿
- 基于 `seq` 和 `checkpoint` 的回放基础能力
- 规则引擎诊断能力
- LLM 辅助诊断的接口预留

### 3.2 非本期重点

- 一开始就建设完整的通用规则库
- 一开始就保存全部原始 prompt 与全部中间流式片段
- 一开始就将回放能力做到跨会话、跨版本、跨模型的完全严格复现
- 一开始就引入复杂的智能根因分析或自动修复闭环

## 4. 前置条件与依赖

当前计划建立在以下前提上：

- 上下文工程已完成基础设计，能够稳定生成 `context pack`
- `context pack` 可提供 `contextPackId`、`selectedMemoryIds`、`droppedMemoryIds`、摘要块与最终注入结果
- 当前 Agent 链路已存在 run、step、tool、文本流等事件来源
- 前后端已具备基础 trace/time line 展示能力，可作为演进起点

## 5. 落地策略对比

### 5.1 方案 A：实时观测优先，回放能力延后增强

先把实时链路看清楚，并同步建设事件持久化底座；回放 UI、run 对比与高级复盘能力进入第二阶段。

特点：

- 优先解决“当前运行发生了什么、哪里出错了、为什么停了”
- 对现有流式链路侵入更小，便于快速验证数据模型和事件质量
- 能更早发现事件缺口、字段缺口与链路不一致问题
- 与当前更新后的方案文档保持一致

### 5.2 方案 B：回放能力优先，先做完整复盘闭环

优先把事件落盘、checkpoint 恢复、回放控制器和复盘 UI 做完整，再补实时观测体验。

特点：

- 事后分析能力更完整
- 对事件完整性和恢复精度要求更高
- 前期实施复杂度高，容易因为数据质量不稳定而反复返工
- 会放大上下文、流式事件、断线补偿尚未稳定时的系统耦合

### 5.3 对比结论

| 对比维度 | 方案 A | 方案 B |
|---|---|---|
| 实施复杂度 | 中，适合分阶段推进 | 高，前期耦合面较大 |
| 与现有链路兼容性 | 高，可沿现有 trace 演进 | 中，需要较早引入完整回放约束 |
| 风险暴露速度 | 快，便于尽早发现数据问题 | 慢，通常要做完整链路后才能暴露问题 |
| 用户价值到达速度 | 快，先解决实时可观测性 | 中，价值偏向复盘场景 |
| 后续扩展性 | 高，可平滑扩到 replay 与 diff | 高，但前期成本更高 |

### 5.4 推荐方案

推荐采用方案 A：`实时观测优先，事件底座同步建设，回放与 run 对比分阶段补齐`。

推荐理由：

- 与当前已更新的 `AGENT_OBSERVABILITY_REPLAY_PLAN.md` 保持一致
- 更符合“先把链路看清，再做高保真复盘”的工程节奏
- 有利于先跑通规则引擎诊断，再逐步引入 LLM 辅助诊断
- 能更好复用已经完成的上下文工程成果，降低初期不确定性

## 6. 总体实施原则

- 以结构化事件为中心，不以原始流文本为中心
- 以可诊断为优先，不以全量存储为优先
- 以增量兼容旧事件为优先，不做一次性协议切换
- 以低侵入接入现有执行链路为优先，不做大范围重构
- 以“规则引擎先落地，LLM 能力后接入”为诊断策略
- 以“热数据服务实时 UI，冷数据服务回放查询”为存储策略

## 7. 目标架构与交付边界

实施完成后，系统应形成以下四层能力：

### 7.1 事件采集层

负责从 run、route、agent step、tool、assistant stream、checkpoint、error 等节点采集结构化事件，并统一编号、排序、关联父子关系和时间戳。

### 7.2 运行态观测层

负责实时展示当前 run 的执行时间线、span 树、文本输出节奏、工具调用状态和实时诊断结果，支撑“边运行边排障”。

### 7.3 持久化与查询层

负责按记录粒度策略保存事件日志、checkpoint 索引、聚合文本、诊断结果与必要的上下文引用信息，并支持按 `runId`、`seq`、事件类型、状态进行检索。

### 7.4 回放与诊断层

负责基于事件日志和 checkpoint 恢复回放视图、对比不同 run 的执行差异，并输出规则引擎诊断结果；后续可在同一接口上接入 LLM 辅助诊断。

## 8. 与上下文工程的衔接要求

观测系统必须将“看见模型输入了什么上下文”纳入链路诊断范围，因此需要明确以下联动：

- `run` 级别关联 `contextPackId`
- 记录本次执行所使用的 `selectedMemoryIds`
- 记录被预算裁剪的 `droppedMemoryIds`
- 记录注入摘要块数量、来源层级和版本信息
- 记录记忆注入失败、缺失、重复注入等异常线索

观测系统不直接保存完整记忆库原文，而是保存“可回溯引用 + 摘要 + 版本”，真正回溯时再按引用访问上下文工程侧数据源。

## 9. 分阶段实施计划

## 9.1 Phase 0：实施准备与边界冻结

目标是冻结核心名词、事件口径、字段边界和保留策略，避免开发中反复返工。

交付物：

- 数据对象词汇表
- 事件类型清单与映射表
- 记录粒度与保留期策略
- 脱敏与权限边界说明
- 与上下文工程的字段对齐清单

完成标准：

- run、span、event、checkpoint、diagnostic_issue 的字段边界清晰
- `contextPackId` 及 memory 引用字段口径统一
- 事件命名兼容旧协议的映射关系已确认

## 9.2 Phase 1：数据模型与事件归一化

目标是建立统一运行数据模型，并将现有链路事件映射进统一结构。

交付物：

- 统一运行对象模型
- 事件归一化策略
- `seq` 编排与父子 span 关联规则
- 旧事件到新结构的兼容映射

关键工作：

- 定义 run、span、event、checkpoint、diagnostic_issue 的职责边界
- 补齐 route、tool、text、error、checkpoint 的统一事件字段
- 确保每个关键事件都能落到对应 span 上
- 明确事件状态流转和异常终止规则

完成标准：

- 任意一次 run 都能形成完整的结构化链路骨架
- 同一事件在实时 UI 与持久化层中的语义一致
- 旧事件源不会因为新模型接入而失去可读性

## 9.3 Phase 2：实时观测 MVP

目标是完成面向当前执行过程的观测能力，让用户在 run 进行中即可判断链路是否正常。

交付物：

- 实时 run 时间线面板
- span 树与关键事件联动展示
- 实时诊断抽屉
- 上下文注入概览区

关键工作：

- 展示 run、step、tool、text、checkpoint、error 的时间顺序
- 展示工具调用耗时、状态、失败原因和重试情况
- 展示 route 决策摘要与上下文注入摘要
- 支持按事件类型和 span 类型快速筛选

完成标准：

- 实时界面可还原“此刻执行到了哪里”
- 工具失败、链路中断、路由异常、上下文缺失能被第一时间发现
- UI 不依赖最终答案生成完成后才可用

## 9.4 Phase 3：事件持久化与断线补偿

目标是让实时链路具备复盘基础，并确保 SSE 中断后数据仍然连续可追。

交付物：

- 事件日志持久化能力
- checkpoint 索引能力
- 文本聚合存储策略
- 断线重连事件补偿机制
- 查询接口与按需加载策略

关键工作：

- 按 P0、P1、P2 粒度落盘
- 建立单 run 的事件数量和字节预算控制
- 明确热数据与冷数据的职责分层
- 设计按 `runId + seq` 查询、分页与窗口化读取能力

完成标准：

- SSE 断线重连后不会出现明显的事件重复与缺段
- 单 run 数据量在预算内可控
- 持久化结果足以支撑后续 replay 基础能力

## 9.5 Phase 4：规则引擎诊断能力

目标是先用确定性规则覆盖高频故障，让系统具备第一版可解释诊断结果。

交付物：

- 诊断规则引擎框架
- 诊断规则分类体系
- 诊断证据结构
- 建议动作模板

首批建议覆盖的高频诊断类别：

- 路由误判或路由缺失
- 工具失败、超时、空结果或结果异常
- 上下文注入缺失、重复注入、裁剪异常
- 文本流中断、未正常结束、done 缺失

规则设计要求：

- 每条规则必须产出 `category`、`severity`、`title`、`reason`、`evidence`、`suggestion`
- 每条规则必须能关联到具体 run 与 span
- 同类诊断要支持去重和聚合
- 规则执行不可阻塞主链路

完成标准：

- 高频问题至少命中一条可读诊断
- 诊断结果能回指事件证据
- 前端可按严重级别和问题类别过滤诊断

## 9.6 Phase 5：回放能力与 run 对比

目标是在持久化事件之上补齐事后复盘体验，支持按 `seq` 和 `checkpoint` 恢复执行视图。

交付物：

- Replay 控制器
- 回放时间轴与跳转能力
- checkpoint 快速恢复能力
- run 对比视图

关键工作：

- 保证回放态与实时态状态隔离
- 支持按 `seq` 单步播放、暂停、快进和定位
- 基于 checkpoint 做恢复锚点，不用其替代完整事件日志
- 支持查看 route、tool、text 的时序差异

完成标准：

- 任意一个已完成 run 都可以被按事件顺序复盘
- 同一问题的多次 run 可直观看到决策和结果差异
- 回放模式不会污染实时观测状态

## 9.7 Phase 6：LLM 辅助诊断接口预留

目标不是立即上线 LLM 诊断，而是保证后续可平滑接入。

交付物：

- 诊断输入装配接口
- 诊断输出标准结构
- 规则引擎与 LLM 诊断的协作边界
- 安全与成本控制约束

设计要求：

- 规则引擎产物仍然是默认主诊断来源
- LLM 只消费已脱敏、已裁剪、结构化后的诊断上下文
- LLM 输出不能直接覆盖规则结果，而应作为补充建议或候选解释
- 必须保留模型版本、调用时间、输入摘要和输出摘要，便于审计

完成标准：

- 不修改现有规则引擎数据结构即可接入 LLM 辅助诊断
- LLM 诊断缺席时，主链路能力不受影响

## 10. 模块拆分建议

为降低耦合，建议将实施任务拆为以下模块并分工推进：

- 运行模型与事件协议模块
- 实时 trace store 与 UI 模块
- 持久化与查询模块
- checkpoint 与 replay controller 模块
- 规则诊断引擎模块
- 上下文联动与引用回溯模块
- 安全、脱敏、TTL 与清理模块

其中建议优先并行推进的组合为：

- `运行模型与事件协议` + `上下文联动字段对齐`
- `实时 trace store 与 UI` + `规则诊断引擎`
- `持久化与查询` + `断线补偿`

## 11. 里程碑与验收

### 11.1 里程碑 M1：链路数据统一

验收重点：

- 所有关键事件已纳入统一模型
- run 与 span 关系稳定
- 上下文注入信息可以被挂接到 run

### 11.2 里程碑 M2：实时观测可用

验收重点：

- 时间线可实时更新
- 规则诊断可实时出现
- 用户可以在执行过程中定位故障位置

### 11.3 里程碑 M3：持久化与补偿可用

验收重点：

- run 结束后事件可查
- SSE 中断后不会出现明显的数据缺口
- 数据量与存储成本在预算范围内

### 11.4 里程碑 M4：回放基础可用

验收重点：

- 已完成 run 可以按 `seq` 回放
- checkpoint 可以作为恢复锚点
- run 对比可以看见关键差异

### 11.5 里程碑 M5：LLM 接口预留完成

验收重点：

- 规则引擎输出已标准化
- LLM 输入装配边界清晰
- 未启用 LLM 时系统行为保持稳定

## 12. 数据治理与安全要求

实施过程中必须同步建设以下治理策略：

- 事件日志分级存储，不默认保存全部原文
- prompt、tool output、assistant output 按粒度和预算保存
- 结构化诊断证据优先于原始文本堆积
- 支持按会话、按 run、按保留期清理
- 对敏感字段做脱敏、摘要化或引用回溯，不直接明文长期保留
- 对内部观测页面增加访问边界，避免普通用户直接接触底层运行细节

## 13. 风险与控制措施

### 13.1 事件量膨胀

风险说明：

- 流式文本、tool output 和中间事件如果无预算控制，容易造成存储和查询成本快速失控。

控制措施：

- 执行 P0、P1、P2 分级存储
- 建立单 run 事件上限与字节预算
- 默认只保存必要原文与聚合文本

### 13.2 事件语义不一致

风险说明：

- 实时 UI、持久化层和回放层对同一事件的解释不一致，会导致“看起来能跑，实际上无法复盘”。

控制措施：

- 统一事件模型和状态流转
- 先完成 Phase 1 再推进后续模块
- 对关键事件做端到端验收样例

### 13.3 实时态与回放态互相污染

风险说明：

- 如果共用状态但缺乏隔离，回放操作可能污染实时运行界面，造成误判。

控制措施：

- 实时态与回放态严格分离
- replay controller 单独维护播放状态
- 明确 store 的只读视图和可变状态边界

### 13.4 诊断规则失控扩张

风险说明：

- 过早构建庞大规则库，会让维护成本和误报率快速上升。

控制措施：

- 先覆盖四大高频故障
- 规则按分类和优先级分层演进
- 保留诊断命中率和误报率复盘机制

### 13.5 LLM 诊断引入后可信度下降

风险说明：

- 如果没有明确边界，LLM 诊断可能制造额外解释噪声。

控制措施：

- 规则结果优先
- LLM 结果标记为辅助解释
- 保留输入输出摘要与审计信息

## 14. 需要确认的事项

在正式实施前，建议最终确认以下事项：

- `context pack` 相关字段是否已经稳定，可直接被 run 引用
- 观测页面是否只面向内部运营/开发使用，还是会暴露给普通用户
- P1/P2 级别数据的默认 TTL 和删除策略是否已有统一标准
- run 对比是否只比较同一会话内执行，还是允许跨会话对比
- LLM 辅助诊断未来是否需要接入模型评估与质量回溯链路

## 15. 推荐执行顺序总结

推荐按以下顺序实施：

1. 先冻结事件模型、字段边界、存储粒度和安全规则。
2. 再完成事件归一化与上下文字段对齐。
3. 先交付实时观测 MVP 与规则引擎诊断。
4. 同步建设持久化、断线补偿和查询能力。
5. 在数据质量稳定后补齐 replay 与 run 对比。
6. 最后接入 LLM 辅助诊断接口，但不改变规则引擎主导地位。

按照这个顺序推进，可以把“先看清、再存稳、后复盘、最后增智”的链路拆开，减少一次性耦合过高带来的返工风险。
