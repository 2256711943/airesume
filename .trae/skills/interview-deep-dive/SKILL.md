# 项目细节面试应答（六维深度框架）

本技能用于在被问及项目细节时，产出**具体、真实、有深度**的面试回答。回答必须锚定本仓库的真实代码，禁止凭空编造。

## 触发场景

- 用户问"这个功能是怎么实现的 / 面试官问我 XXX 怎么答"
- 用户问"项目难点是什么 / 为什么选这个方案"
- 用户要求准备面试、模拟追问、复盘项目亮点
- 用户粘贴面试官问题要求生成应答

## 核心工作流（先取材，再作答）

**第 0 步：取材（强制）。** 作答前必须先在代码库中定位真实实现，收集以下素材：

1. `Grep` 关键模块名/核心函数名，`Read` 定位到真实文件与行号；
2. 检索项目内已有的面试复盘文档（文件名含 `INTERVIEW` / `QA` 的 `.md`），它们是第一手素材源；
3. 收集可引用的硬证据：关键代码片段（≤15 行）、配置常量、类型定义、目录结构；
4. 收集可量化数据：阈值、批量大小、缓存 TTL、帧预算、词/秒等出现在代码或配置中的数字。

**找不到的细节**：明确标注"这是行业通用值/估算假设"，不得伪装成项目实测值。

## 六维应答框架

每个维度都给出【要求】与【句式】。回答按 ①→⑥ 顺序组织。

### ① 项目难点（Why Hard）

- 【要求】说清问题背景与约束，用**规模数字**体现难度（数据量、并发量、频率、时限）。难点必须落在具体矛盾上，如"流式输出与 Markdown 增量渲染冲突"、"断线期间事件丢失导致状态漂移"。
- 【句式】"在 <场景> 下，<约束/规模>，导致 <具体矛盾>，常规做法 <为什么不够用>。"

### ② 具体实现细节（How）

- 【要求】按 数据流/架构分层 → 核心算法/数据结构 → 关键代码 三层展开。必须引用真实代码：
  - 用 Markdown 链接指向真实文件：`[文件名](file:///绝对路径#L起-L止)`
  - 代码片段控制在 15 行内，只贴最能说明设计的部分；
  - 说明数据结构选型理由（如为什么用 Map 而不是数组、为什么带 seq 字段）。
- 【句式】"整体链路是 A → B → C。其中 B 的核心在 [xxx.ts](file:///...) 的 xx 函数：……"

### ③ 决策依据（Why This Way）

- 【要求】给出完整推理链：**当时的问题 → 需求约束（列出 2-4 条硬约束）→ 候选方案 → 逐条对比 → 结论**。让面试官看到"是被约束逼出来的选择"，而不是"跟风用了新技术"。
- 【句式】"当时的核心约束是 X 和 Y。方案 A 不满足 X，方案 B 引入 Z 成本，因此选 C，代价是接受 D。"

### ④ 替代方案分析（Trade-offs）

- 【要求】至少 1-2 种可行替代方案，用对比表呈现：方案 / 优点 / 缺点 / 适用场景 / 落选原因。承认所选方案并非银弹，指出它的失效边界。
- 【模板】

| 方案       | 优点 | 缺点 | 适用场景 | 落选原因 |
| ---------- | ---- | ---- | -------- | -------- |
| 所选方案 C |      |      |          | —        |
| 替代方案 A |      |      |          |          |
| 替代方案 B |      |      |          |          |

### ⑤ 行业参考案例（Industry Evidence）

- 【要求】至少引用 1 个大厂（Google、Amazon、Meta、阿里、腾讯、字节等）在同类问题上的公开实践，说明其设计思路与本项目方案的异同、可借鉴之处。不确定的资料用 `WebSearch` 查证，禁止编造。
- 【句式】"这个问题业界有先例：<公司> 的 <系统> 用 <思路> 解决，和我们的差异在于 <约束不同>，可借鉴的是 <点>。"
- 【常见主题 → 案例映射（查证后引用）】
  - 流式输出/打字机渲染 → ChatGPT 的 SSE 分块流式、Notion AI 增量渲染
  - 可靠事件流/断线重连 → Kafka offset 消费、SSE Last-Event-ID、直播 seq 连续性校验
  - 协同编辑/状态同步 → Google Docs OT、Figma CRDT、腾讯文档
  - 长连接保活 → 微信/钉钉心跳与重连退避策略
  - 渲染性能 → Chrome rAF 合帧、React Fiber 时间切片、虚拟列表（react-window / Element Plus virtualized）

### ⑥ 现状缺点与优化方向（Self-awareness）

- 【要求】主动暴露 2-3 个真实局限（可从代码 TODO、已知坑、压测数据推导），每条配一个**可落地的优化路径**（改什么、预期收益量级）。体现客观判断力，这是区分"背题"与"做过"的关键。
- 【句式】"目前 X 在 <场景> 下有瓶颈，表现为 <现象>。优化方向是 <改法>，预期 <量级收益>，但需要 <成本>。"

## 回答结构

1. **讲述版（详细叙事，代替"30 秒版"）**：一段连贯的完整故事——背景/规模 → 具体矛盾 → 你采取的动作 → 核心机制 → 量化结果 → 主动承认代价与边界。必须细节落地，禁止只贴空泛公式，让面试官一眼看出"这是你踩过的坑，不是背的模板"；
2. **六维展开**：按 ①→⑥ 详述（供深挖）；
3. **追问预判**：列出 3-5 个面试官最可能追问的问题，附一句话答法。

## 真实性红线

- 所有代码引用必须来自真实文件，路径与行号可验证；
- 数字必须来自代码/配置/文档/用户口述，其余标注"估算/行业通用值"；
- 禁止空泛词："优秀的架构"、"大幅提升性能"、"高可用高并发"——必须换成具体机制与数字；
- 不确定的大厂案例宁可查证（WebSearch）或删掉，不可编造。
