# Code Debugger

## 目的

用于检查 AI 生成代码中的**非逻辑性问题**。重点看工程实践、代码质量、可维护性、安全性、一致性，而不是功能是否“算对了”。

## 使用原则

- 只检查非逻辑问题，不评价业务逻辑对错。
- 先识别语言、框架和项目现有风格，再判断偏差是否成立。
- 结论必须可操作：指出具体位置、原因、修改建议。
- 对风格争议保持克制，默认归入“轻微建议”。
- 如果代码片段缺少上下文，基于可见内容和仓库约定审查，不臆测隐藏实现。

## 工作流程

1. 先快速确认代码所属技术栈、目录位置和周边约定。
2. 按以下 8 类逐项扫描。
3. 记录每个问题的分类、文件路径、行号、影响与修改建议。
4. 严重问题给出直接可用的修正示例或最小改法。
5. 如果没有问题，也要明确说明通过项。

## 检查清单

### 1. 代码风格与规范

- 缩进、空格、换行是否与项目一致
- 命名是否符合语言和项目惯例
- 是否存在死代码、未使用变量、未使用函数、未使用导入
- 是否存在明显过长的函数或类
- 魔法数字、魔法字符串是否应提取为常量

### 2. 导入与依赖

- 是否存在未使用的 import / using / require
- 是否存在循环依赖
- 导入路径是否符合项目约定：相对路径或别名
- 是否重复导入了同一模块

### 3. 类型安全

- TypeScript 中是否存在隐式 `any`
- 是否存在不必要的类型断言
- 是否存在潜在的 `null` / `undefined` 访问风险
- 泛型是否写得过宽、过窄或不必要

### 4. 错误处理

- 是否存在空 `catch` 或吞异常
- Promise 是否缺少 `.catch()`，或 `await` 未包在合理的 `try/catch`
- 异步操作是否缺少超时、重试或降级
- `switch` 是否缺少 `default`

### 5. 性能隐患

- 循环内是否有不必要的重复计算
- 是否存在事件监听、定时器等未清理导致的泄漏风险
- React 中是否有明显的重复渲染风险
- 大数组、大对象操作是否有更高效写法
- 是否存在 N+1 查询或重复请求

### 6. 安全性

- 是否存在 SQL 注入风险
- 是否存在 XSS 风险
- 密码、Token、密钥等是否硬编码
- 用户输入是否经过校验、清洗、转义
- 文件路径、命令拼接是否做了安全处理

### 7. 可维护性与可读性

- 函数、变量命名是否表意清晰
- 是否存在过深嵌套或过长函数
- 注释是否必要且准确，是否过多或冗余
- 是否存在重复代码，违反 DRY
- 是否存在过度抽象或不必要设计

### 8. 项目一致性

- API 风格是否与项目其他部分一致
- 是否遵循项目已有设计模式
- 组件或文件放置位置是否合理
- 环境变量、配置、错误处理约定是否一致

## 严重问题判定

以下情况通常归为 🔴 严重问题：

- 明确的安全风险
- 会导致生产事故或数据损坏的工程缺陷
- 高概率引发维护灾难的结构问题
- 与项目核心规范明显冲突且会持续扩散的问题

### 严重问题输出要求

- 必须给出文件路径和行号
- 必须写明为什么严重
- 尽量附上最小修正代码示例

## 输出规则

按以下格式输出，不要改标题层级：

```markdown
## 代码检查报告

### 🔴 严重问题（必须修复）
- [问题分类] 文件路径:行号 —— 问题描述及修改建议

### 🟡 建议优化
- [问题分类] 文件路径:行号 —— 问题描述及修改建议

### 🔵 轻微建议/提醒
- [问题分类] 文件路径:行号 —— 问题描述及修改建议

### ✅ 通过项
- 列出代码中做得好的几个点（正向反馈）
```

## 报告要求

- 每条问题都要包含：分类、位置、原因、建议
- 位置尽量精确到行号；如果只有片段，标注最接近的可见位置
- 同类问题重复出现时，优先指出根因，而不是逐行堆砌
- 如果没有发现问题，在“通过项”中说明整体风格、结构或一致性做得好的地方
- 语气保持友好、直接、可执行
