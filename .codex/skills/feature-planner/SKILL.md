# Feature Planner - 功能方案设计技能

## Overview

当用户提出新的需求或功能请求时，此 skill 强制要求 AI **先出方案，并且先不要给出具体实现代码**。它定义了一套结构化的方案产出流程，确保每个功能变更都经过需求理解、多方案对比、推荐决策和落地规划四个阶段，避免跳过分析直接编码导致的返工和设计缺陷。

该技能需要结合项目文档体系（`PRD.md`、`OPENAPI.yaml`、`AI_SPEC.md`、`CODE_STYLE.md` 等）和现有代码库进行分析，并遵守 [AGENT.md](file:///d:/aiprogram/aitext/.codex/AGENT.md) 中的规范优先级和执行规则。

## 使用场景

- 用户提出新的功能需求（如"增加一个简历评分页面"）
- 用户要求修改或扩展现有功能（如"优化简历解析逻辑"）
- 用户询问某个功能的实现方案或技术选型
- 用户要求评估一个需求的可行性和工作量
- 用户要求多个实现方案进行比较分析

## 方案产出流程

### 阶段 1：需求理解与上下文分析

在开始任何设计之前，必须先完成以下分析：

1. **需求澄清**
   - 复述对用户需求的理解，确认需求意图和预期目标
   - 如果需求有歧义或含糊之处，先通过提问澄清

2. **项目上下文遍历**
   - 搜索项目中与需求相关的现有模块、文件结构、数据模型
   - 阅读相关文档（PRD、API 规范、数据库 Schema 等）
   - 阅读相关代码文件，了解现有实现方式

3. **现状评估**
   - 盘点已有基础设施（组件、服务、工具函数、Composables）
   - 识别可复用的现有代码和资源
   - 评估当前项目状态对需求的支撑程度

**产出物**：需求理解摘要 + 上下文分析报告（涉及的文件列表、现有能力的评估）

### 阶段 2：方案设计

基于上下文分析结果，设计 ** 2 种** 候选方案。每种方案需要包含：

- **核心思路**：方案的设计理念和关键技术决策
- **关键实现路径**：实现该方案的主要步骤
- **涉及的文件改动范围**：列出需要新增、修改或删除的文件

#### 方案对比表格

必须使用以下格式进行方案对比：

| 对比维度 | 方案 A | 方案 B | 方案 C（如有） |
|---------|--------|--------|-------------|
| 实现复杂度 | 高/中/低 + 说明 | 高/中/低 + 说明 | 高/中/低 + 说明 |
| 与现有代码耦合度 | 高/中/低 + 说明 | 高/中/低 + 说明 | 高/中/低 + 说明 |
| 可复用性 / 扩展性 | 高/中/低 + 说明 | 高/中/低 + 说明 | 高/中/低 + 说明 |
| 可维护性 | 高/中/低 + 说明 | 高/中/低 + 说明 | 高/中/低 + 说明 |
| 性能影响 | 正面/负面/无影响 + 说明 | 正面/负面/无影响 + 说明 | 正面/负面/无影响 + 说明 |
| 风险等级 | 🔴/🟡/🟢 + 说明 | 🔴/🟡/🟢 + 说明 | 🔴/🟡/🟢 + 说明 |

### 阶段 3：方案推荐

基于方案对比，明确给出推荐：

1. **推荐方案**：明确指出推荐哪个方案
2. **推荐理由**：
   - 在这个项目上下文和当前时间节点上，为什么选择它
   - 它如何更好地平衡了复杂度、可维护性和业务需求
3. **被淘汰方案说明**：
   - 指出不推荐方案的致命缺陷或不适合的原因
   - 说明在什么条件下这些方案可能变得可行

### 阶段 4：落地计划

对推荐方案给出详细的落地计划：

1. **分步实施步骤**
   - 每个步骤的具体任务
   - 涉及的文件
   - 预估工作量

2. **依赖关系**
   - 标注哪些步骤可以并行执行
   - 标注哪些步骤有前后依赖关系

3. **影响范围**
   - 每个步骤对现有功能的影响
   - 是否需要同步更新文档（`OPENAPI.yaml`、`PRD.md`、`DB_SCHEMA.md` 等）
   - 是否需要迁移数据或兼容旧版本

4. **验收标准**
   - 每个步骤完成的可验证标准
   - 测试要点

## 必须遵守的原则

1. **最小改动原则**：能不改就不改，能小改不大改，优先复用现有代码
2. **项目一致性**：新代码的风格、命名、目录结构、设计模式必须与项目现有代码保持一致
3. **文档对齐**：如果方案涉及接口变更、数据模型变更，必须同步更新对应的文档（`OPENAPI.yaml`、`PRD.md`、`DB_SCHEMA.md` 等）
4. **向后兼容**：方案不能破坏现有功能，必须考虑兼容性
5. **优先复用**：在引入新依赖前，先检查项目中是否已有同类工具/组件/服务可以复用
6. **规范优先级**：遵循 [AGENT.md](file:///d:/aiprogram/aitext/.codex/AGENT.md) 中定义的规范优先级（PRD > OPENAPI > ... > CODE_STYLE）

## 禁止行为

- ❌ **不能直接跳步骤给代码** —— 必须先出方案，等待用户确认后再落地
- ❌ **不能引入未使用的框架或库** —— 除非方案对比中明确指出需要引入并说明理由
- ❌ **不能绕过项目现有规范** —— 必须遵守 `AGENT.md`、`CODE_STYLE.md` 等规范
- ❌ **不能只给一个方案** —— 必须对比至少 2 种方案
- ❌ **不能擅自扩展需求范围** —— 不得越过 PRD 扩展业务范围
- ❌ **不能提交"顺手重构"** —— 不得提交未在变更说明中提到的非相关改动
